# BIM Viewer — ThatOpen / OBC wiring (this app)

> Status: seed — expand as you work this area.
> Documents how **this project** wires ThatOpen. How to *build* a generic OBC component → `_thatopen-bim-component` skill. ThatOpen API reference → start at `docs/ThatOpen_docs/INDEX.md`. Do not duplicate those here.

## Overview

The 3D world is a singleton bootstrapped once in `bim-components/setup/` — never inside React. React reaches the engine through `bimStore`. `<bim-*>` BUI web components are normally confined to `ViewportWrapper.tsx` (shadow-DOM isolation); everywhere else uses plain React (`LeftPanel`/`RightPanel`, toolbar components). The **Drawing Editor** tab is the one documented exception — its SheetBoard web components (`<bim-sheet-board>`, `<bim-paper-space>`, `<bim-checkbox>`) live in that feature's React panes (see the Drawing Editor section). ThatOpen libs are pinned to **v3.4.x**.

## Patterns & conventions

- **Cloud auto-load is per-project & opt-out.** `useAutoLoadCloudModels` loads every `.frag` under a project's `02_frag` folder on open, gated by the `auto_load_cloud_models` boolean column on `projects` (`DEFAULT true`, additive). The toggle lives in `CloudModelModal.tsx`'s header, is admin-only (`useIsProjectAdmin`; non-admins see it read-only, not hidden), and is read/written through the `projects` **table** via `useProject`/`useUpdateProject` (the modal's single-project path: `getProjectById` hits `projects` directly) — *not* the `active_projects` view. Any consumer that reads through `active_projects` (e.g. the project **list**, `useProjects` → `getProjects`) needs the view to expose the column too; the view definition isn't in tracked migrations, so it must be inspected live and updated in the same migration or those reads miss it. Disabling only suppresses the *next* auto-load; it never unloads models already in the viewer, and manual load (Cloud Models picker, Load IFC/FRAG) is unaffected. The bail in `useAutoLoadCloudModels` sits **after** the project-switch dispose block so switching into a disabled project still cleans up the previous project's models.
- **Cloud loading progress is one shared, store-driven surface — and cancellable.** Both the manual picker (`CloudModelModal` → `handleLoadSelected`) and auto-load funnel through `useLoadCloudModelBatch`, which drives `bimStore`'s `isModelLoading`/`loadingFiles` (per-file `pending`→`loading`→`done`/`error`/`cancelled`). `CloudModelLoadingModal` renders purely from that state — it never calls the loader. The batch runs in waves of `MAX_PARALLEL = 10`. **Stop:** the loader creates one `AbortController` per run and stashes it via `setLoadingAbortController`; the modal's "Stop Download" button (shown while `!isDone`) calls `bimStore.cancelModelLoading()`, which `.abort()`s the in-flight `supabase.storage.download(path, {}, { signal })` requests (signal is the **third** arg, not options) **and** flips every non-terminal file to `'cancelled'` in one atomic set. The loader's per-file `catch` treats `signal.aborted` as a cancel (not `'error'`, doesn't set `hasError`), and skips loading any download that resolved just as the abort landed (`if (signal?.aborted) return` before `fragments.core.load`) so a cancelled file never enters `loadedModelIds`. Cancel is **keep-what-loaded**: already-`done` models stay in the viewer (no rollback). `'cancelled'` counts as terminal for the modal's `isDone`, so it swaps to "Close & View Viewer"; only a fully clean run auto-dismisses (1s). The controller is cleared on finish (guarded so it can't null a newer run's controller).
- **2D Views (plans + elevations) auto-generate on load.** The built-in `OBC.Views` is wired in `setup/src/views.ts` (`setupViews` sets `views.world` + `OBC.Views.defaultRange`), registered in `setup/index.ts`. UI is `components/bim/Views2DList.tsx` — a "2D Views" `PanelSection` under Models List on the Models tab (plain React, no `<bim-*>`). It subscribes a **debounced regenerate-all** to *both* `fragments.list.onItemSet` **and** `onItemDeleted`: `views.close()` → `views.list.clear()` → `createFromIfcStoreys()` + `createElevations({ combine: true })`. Clear-and-recreate is safe because this section owns the list (no user-created section views in this cut) — the later interactive-sections feature must preserve user views instead. Plans vs elevations are grouped by diffing `views.list.keys()` before/after each create call (the key is the `open(id)` argument). Effect cleanup removes only the fragment listeners — it never touches `views`/camera (ViewportWrapper owns world teardown; `world.camera` throws once disposed).
- **Plans open in perspective, straight-down.** `OBC.Views.open(id)` sets `world.camera` to the view's own `OrthoPerspectiveCamera`, configured (at `world`-set time in the engine) as **Orthographic + "Plan" nav mode** (pan + zoom, rotation speed zeroed). For plan rows only, `Views2DList.applyPerspectivePlanCamera` flips just the projection to **Perspective** (`projection.set("Perspective")` + `updateAspect()`) and leaves everything else — the camera stays straight-down and Plan mode keeps it locked to a top view (no tilt, no orbit). It then calls **`camera.fitToItems()`** because OBC's ortho→perspective switch reuses a stale camera distance and would otherwise leave the model off-screen (user having to press Focus); `fitToItems` → `controls.fitToSphere` keeps the current straight-down direction, so it only re-frames and never reintroduces a tilt. Elevations skip all of this (stay orthographic). Exit is `views.close()` → OBC's `world.useDefaultCamera()`, so no cleanup is needed. Camera changes are made visible by `resyncPostproductionCamera` (`postproduction.updateCamera()`) — the composer otherwise keeps rendering the pre-swap camera. (A tilted "2.5D" variant was tried and reverted: straight-down perspective reads as a clean top view, whereas the tilt looked off.)
- OBC bootstrap is a **singleton** in `setup/` — React never constructs the world.
- **React ↔ custom-component pattern:** a custom `OBC.Component` owns all engine state and exposes methods/getters + an `onChanged` event; a React feature panel drives it via `components.get(...)` and re-renders on `onChanged`. Precedents: `GisPanel` ↔ `GisLayers`, `DrawingEditorPanel`/`DrawingEditorBoard` ↔ `DrawingEditorSetup`.
- **New OBC component — step checklist** (moved from CLAUDE.md; follow the `_thatopen-bim-component` skill for the full workflow):
  1. Use `_thatopen-bim-component` skill
  2. Place in `bim-components/`
  3. Extend `OBC.Component`, implement `OBC.Disposable`
  4. Use `OBC.Disposer` for all Three.js meshes
  5. Unbind DOM events in `dispose()`
  6. Register in `bim-components/setup/` (singleton)
- `<bim-panel>`/`<bim-grid>`/`<bim-*>` never outside `ViewportWrapper.tsx` — **except** the Drawing Editor tab, whose SheetBoard/paper-space web components live in `features/drawing-editor/`.
- Theme via CSS vars (`--bim-*`) in `style.css @theme {}` — no inline overrides.
- Before any OBC feature: check v3.4.x API (breaking changes from v2) via the docs navigator.

## Camera navigation (cursor-bounded zoom + hover pivot)

`src/bim-components/CursorZoom/index.ts` — always-on, no toolbar entry, registered in `setup/index.ts`. Navisworks-like: the surface under the cursor bounds how far the camera may travel and becomes the orbit pivot.

- **`minDistance` is dead config out of the box, and `infinityDolly = false` is what revives it.** `SimpleCamera.newCameraControls()` ships `dollyToCursor = true` (zoom already aims at the cursor), `infinityDolly = true` and `minDistance = 6`. In `_dollyInternal`, `if (infinityDolly && dollyToCursor) _dollyToNoClamp(distance)` **skips `clampedDistance` entirely** and pushes the *target* forward instead — the infinite fly-through. Nothing else in the clamp works until that flag is off.
- **Two mechanisms, not one, because `setOrbitPoint()` is animation-unsafe** (vendor: *"SHOULD NOT RUN DURING ANIMATIONS"*, and `smoothTime = 0.2` makes a wheel burst an animation). The **pivot** moves via `setOrbitPoint(hit)` on `pointerdown` (controls at rest); the **clamp** never touches the target and only raises `minDistance`, which `update()` re-clamps every frame. A `pointerdown` landing within `DOLLY_SETTLE_MS` (300 ms) of a wheel event is **skipped, not deferred** — the hit would be stale by the time it settled, and the next click re-pivots.
- **`setOrbitPoint` moves the target without moving the camera**, so pivoting on *every* pointerdown (selection clicks included) has no visual effect. It only means the next orbit spins around what you picked and the next wheel dollies toward it.
- **The clamp is trigonometric, because the pivot is usually stale.** `dollyToCursor` walks the camera along the *cursor ray* while `minDistance` bounds `|camera − target|`, so travel is projected onto the camera→target axis: `minDistance = max(standoff, distance − (dHit − standoff)·cos θ)`, capped at `maxDistance × 0.99` (`clamp(v, min, max)` returns `min` when they cross). Without `cos θ` the stop is ~13% off at the edge of the 60° frustum. Zoom-**out** is never bounded. Cursor over empty space → `minDistance = standoff`, so zooming toward the existing pivot still works.
- **Zoom-step scaling is free.** `_dollyInternal` is multiplicative (`radius × 0.95^-delta`), so the stride is already proportional to distance-to-target; the hover pivot is the only thing needed to make it feel right. Do **not** add a dynamic `dollySpeed` — it would double-scale.
- **Raycasting is lazy: one per gesture.** `pointerdown`, plus the first wheel event of a burst (`CLAMP_CACHE_MS = 150`, stamped *before* the async hop so a 30/s burst can't queue N raycasts), single-flight across both. Nothing is added to the per-`pointermove` budget. `OBF.Hoverer` cannot serve as a free hit source — it exposes no point/distance (only `onHoverStarted`/`onHoverEnded`) and fires on a `delay` *after* the mouse stops.
- **Orbit mode only; the clamp is perspective-only.** Read per gesture, because `OrthoPerspectiveCamera.set(mode)` fires **no event** (`mode` is a cheap getter). In `Orthographic` the wheel maps to `_zoomInternal`, which never consults `minDistance`, and `setOrthoCamera()` pins `distance = 200` — so ortho gets the pivot and step scaling, never the clamp. `FirstPerson` is exempt by design (a walkthrough must pass through walls) and `Plan` (2D views) has no orbit.
- **Controls config is snapshot-and-re-applied, never patched once.** Three things overwrite it: `OrbitMode.activateOrbitControls()` resets `minDistance = 1` / `maxDistance = 300` / `truckSpeed = 2` on **every** `mode.set()`; a `Views2DList` plan open/close swaps `world.camera` for a whole new `CameraControls`; `GisLayer3d` patches `maxDistance = 100000`. Hence the `world.onCameraChanged` → `_bindControls` rebind, and per-gesture recomputation rather than a stored clamp.
- ⚠️ **Restoring a baseline `minDistance` must be floored at the current distance** (`Math.min(baseline, controls.distance)`). `update()` clamps distance into `[minDistance, maxDistance]` every frame, so restoring the vendor's construction-time `6` while the camera sits 0.25 m off a wall would shove it backwards.
- **Standoff is derived, never hardcoded twice:** `max(0.25, camera.three.near × 2.5)`. See the near-plane gotcha below — the near plane is what actually decides how close the camera can get.

### The pivot dot (`CursorZoom/src/PivotMarker.ts`)

A 7px green dot marking what the camera is anchored to, owned and freed by `CursorZoom` (a manager, not a registered component — nothing else drives it).

- **Context-sensitive anchor**, because zoom and rotate only share one after a click: the **hovered hit while zooming** (already raycast for the clamp, so it is free) and **`controls.getTarget()` while rotating**. Showing the true pivot during a zoom would leave the dot floating in mid-air whenever the pivot is stale.
- **A `CSS2DObject`, so there is no render pass, material or per-frame rescaling.** `OBF.PostproductionRenderer` extends the front package's `RendererWith2D`, which owns `three2D: CSS2DRenderer` — the same one drawing `surface-measure-cursor`'s labels. A DOM element is screen-constant by nature and composited above the canvas. ⚠️ It therefore has **no depth test** and shows *through* geometry — correct for a pivot indicator, wrong if it were ever meant to read as paint on a surface. `pointer-events: none`, and `detach()` must `element.remove()` (a `CSS2DObject` leaves its node in the DOM when its object leaves the scene graph).
- ⚠️ **`_object.visible` stays `true` for the marker's whole attached life; opacity is the only switch.** `CSS2DRenderer` sets `display: none` both when `object.visible === false` and when the point leaves the frustum, and a `display` flip in the same frame as an `opacity` change kills the CSS transition — the fades would snap.
- **The wheel emits no `controlstart`/`controlend`** (vendor: scroll events are intermittent, so start/end cannot be detected). So **rotate** is driven by `controlstart` + `control` gated on `controls.currentAction & ROTATE_ACTIONS` — a bitmask, because touch gestures are compound (`TOUCH_DOLLY_ROTATE` is a rotate too) — while **zoom** is driven from `_onWheel` plus the marker's own idle timer. No `controlend` handler is needed: the hold countdown restarts on each `control`, so it begins at the last one.
- **Timing:** 80 ms fade in, 500 ms hold after the last activity, 160 ms fade out. An instant hide makes a fast scroll read as a rendering glitch.
- **Suppressed while `CursorSurface.visible`** — one check that cannot rot, because every cursor-owning tool drives that shared guide (see its `visible` getter). Read the getter; never reach into `.group.visible`.
- **Colour is the `--color-status-ok` design token**, reachable from a DOM node because Tailwind v4's `@theme {}` in `style.css` emits it on `:root`. The 1px `rgba(0,0,0,.55)` ring is load-bearing, not decoration — flat green loses its edge against a pale ceiling.

## Section tool (OBC.Clipper — interactive cut planes)

`ClipperCursor` (`src/bim-components/ClipperCursor/`) wraps `OBC.Clipper` and is the engine behind the right rail's **Clip** menu (`ToolbarClip.tsx`). Max 6 planes. Nothing persists — planes die with the viewport.

**A cut plane has three visual parts, and the change that made this tool usable was pulling them apart.** `OBC.SimplePlane` ships all three welded together; we use one, hide one, and replace one:

| Part | What it is | Where it lives |
|------|-----------|----------------|
| **outline** | `LineLoop` tracing the plane's rectangle, child of `_planeMesh` so `plane.size` scales and `plane.helper` orients it for free | `world.scene` — depth-tests against the model, and *is* clipped by other planes |
| **carrier quad** | `SimplePlane._planeMesh`, kept only to size and orient the outline. Never rendered | `world.scene` |
| **axis gizmo** | A `GizmoAxis` handle (see below). The only drag handle | the overlay scene — clipping suspended, `depthTest: false` |
| ~~drag arrow~~ | `SimplePlane`'s own `TransformControls` — permanently suppressed | — |

- **The plane is drawn as a bare outline with no fill, and is not pickable at all.** This is the whole interaction model: a section that has no surface cannot take a click meant for an element. → why, and the shipped-then-reversed alternative: [ADR-0002](../adr/0002-section-plane-outline-only.md).
- ⚠️ **It must be the *material* that is invisible, not `_planeMesh.visible`.** Hiding the mesh skips its children and takes the outline with it. `plane.planeMaterial` is set to `MeshBasicMaterial({ visible: false })` — the same trick `SimplePlane` uses for its own `_arrowBoundBox`.
- ⚠️ **`SimplePlane.visible` is a triple-duty setter** — it toggles the helper *and* `controls.getHelper()` *and* calls `toggleControls()`. So `_syncVisibility` sets `plane.visible = enabled` and then re-suppresses the default arrow, **every pass**: the arrow springs back otherwise. Outline shows for every enabled plane; the gizmo only for the selected one.
- **Outline colour states the plane normal's dominant world axis** — X green, Y blue, Z red, ties to X then Y (`axisOf()` in `GizmoAxis`). Interaction state therefore rides on **opacity** (idle 0.45 → selected 0.85 → hovered/dragging 1.0), not hue. ⚠️ Not on line weight: `LineBasicMaterial.linewidth` is ignored by `WebGLRenderer` (lines are always 1px) — carrying state there needs `Line2` fat-line geometry.
- **Extent is fixed in world space at `BoundingBoxer` diagonal × 1.0**, with `plane.autoScale = false` (OBC's default is camera-relative, which reads as a badge near the gizmo rather than a plane slicing the model). ⚠️ **Measured when a plane is created, not at load time.** `BoundingBoxer.addFromModels()` unions each `model.box`, and a model is in `fragments.list` while still loading (FRAGS reports `isBusy` as `!_isLoaded || _isProcessing || pendingRequests`), so an `onItemSet`-triggered read can legitimately find an empty box. A plane is only ever created by a click, so that read is always post-processing. The `onItemSet` hook stays to resize *existing* outlines and **bails on an empty box** rather than falling back — falling back is what used to leave a 10-unit outline inside a 40 m building. `ClipperOutlineManager` is the only boxer consumer in the repo that reads at load time; `view-cube.ts` and `ToolbarSettings.tsx` both read on user action.
- **Dragging is our own pointer handling, and `pointerdown` is captured on `window`, not the canvas.** camera-controls and the highlighter listen on the canvas itself, and a capture listener on the same element still runs *after* them (target-phase listeners fire in registration order), so the event has to be stopped one level up. Only the gizmo handle is pickable, so that stop only ever fires over the handle. The drag builds a camera-facing plane containing the normal, intersects the pointer ray with it, and projects the offset onto the normal — so a tilted plane still moves exactly perpendicular to itself. Camera is disabled for the duration, the same way `SimplePlane.changeDrag` does it.
- **Component layout follows MiniMap/PropertyTable**: `index.ts` holds the class, `src/` holds managers, and **each manager owns and frees its own objects** (`ClipperOutlineManager`, `ClipperDragManager`, `ClipperPlacementManager`). Disposal is therefore local, not one central routine. `ClipperDragManager` takes a `pickTargets: () => { mesh, planeId }[]` callback rather than a reference to the gizmo layer, so it never learns `GizmoAxis` exists.
- ⚠️ **`components.get(ClipperCursor as any)` in `ToolbarClip` is deliberate, not sloppiness.** Its 3-arg constructor doesn't match what `OBC.Components.get()` expects. It is now the **last** cursor still doing this: all three measure cursors have moved to the 1-arg constructor + `world` setter (see § Measure tools → Cursor-family constructor typing). `ClipperCursor` needs `viewport` as well as `world`, and its constructor builds all three managers immediately, so migrating it means making that construction lazy — a separate job, not a one-line change.
- **Planes created by other features are left alone.** `ClipperCursor` styles only planes it creates (no `Clipper.onAfterCreate` hook), so the Drawing Editor's own section clip — which sets `plane.visible = false` itself — is untouched.

### GizmoAxis (shared overlay axis gizmos)

`src/bim-components/GizmoAxis/` is a general engine service, not a clipping concept: "give me a world-aligned 3-axis handle at this transform, always drawn on top."

- **One overlay scene and one render pass for every gizmo**, registered on `world.renderer.onAfterUpdate`: it suspends `clippingPlanes`, sets `autoClear = false`, renders, then restores. One shared scene means the second and third consumers cost no extra pass. All materials are `depthTest: false`, which is what makes a handle grabbable wherever it is visible — including when the model stands in front of it.
- **1-arg constructor plus a `world` setter** (`new GizmoAxis(components); gizmoAxis.world = world`), as `SpotCoordinate`/`ArSession`/`Hoverer` do. Consequence worth knowing: `components.get(GizmoAxis)` needs **no cast**. This is the pattern the cursor family is migrating *to* — the three measure cursors now follow it too, leaving `ClipperCursor` as the only component still needing one. Setting `world` re-registers the pass.
- **`create({ follow, grabAxis })` returns an opaque `AxisGizmoHandle`** carrying `picker`, `visible`, `highlighted` and `dispose()`. Consumers keep handles however they like, so there is no shared key namespace to collide in and a disposed handle can't be reused. `ClipperCursor` keeps `Map<planeId, handle>` and builds its own pick list from `handle.picker`/`handle.visible`.
- **It follows its target's *position* only** — rotation is ignored, so green always runs along world X, blue up along Y, red along Z. That's what lets a plane's outline colour name the very arrow that moves it. Screen-constant sizing comes from `GIZMO_VIEW_FRACTION` (a fraction of the viewport's world-space height, handling perspective *and* orthographic cameras) — **the one knob for gizmo size**.
- **Only the arrow matching the plane's colour is grabbable**, wrapped in an invisible cylinder, and it is drawn at `GRAB_AXIS_EMPHASIS` (×1.5) — length, cone *and* picker, so what you can grab stays identical to what you can see. It turns `HIGHLIGHT_COLOR` (yellow) while hovered or dragged. The other two arrows are inert: pulling them would move the outline without changing where the model is cut.
- ⚠️ **Cones are aimed with `quaternion.setFromUnitVectors(CONE_APEX, direction)`, never by composing Euler angles.** A previous `rotZ`/`rotX` scheme sent the −Z cone's apex to **+Z** — its fallback flip about Z fired on top of the flip about X and undid it, so one red arrowhead pointed inward. With a target direction there is no order, sign or per-axis constant left to get wrong. The antiparallel −Y case is safe: `setFromUnitVectors` detects `dot + 1 < EPSILON` and falls back to a half-turn about Z.
- ⚠️ **Cross-component imports inside `bim-components/` must be relative** (`"../GizmoAxis"`), *not* the `@/*` alias that `CLAUDE.md` mandates elsewhere. `tsconfig.json` excludes `src/bim-components/**`, so `vite-tsconfig-paths` never rewrites aliases in that folder: an aliased import **type-checks and then fails the Rollup build**. Every pre-existing file there already imports relatively for this reason.

**Accepted consequence:** the outline lives in `world.scene`, so another enabled plane can clip part of it away. Immunity would mean moving it to the overlay scene, which would also make it immune to *depth* — drawing over the model instead of behind it. `WebGLRenderer.clippingPlanes` is global with no per-material opt-out, so those two properties can't be separated.

## Measure tools (Length / Area / Surface)

The right rail's **Measure** menu (`ToolbarMeasure.tsx`, with `LengthMeasure.tsx` / `AreaMeasure.tsx` / `SurfaceMeasure.tsx` supplying each tool's button + result list). Angle is a "Soon" placeholder. Nothing persists — measurements die with the viewport.

**Length and Area are one component family; Surface is a different animal.** `src/bim-components/MeasureCursor/` holds `LengthMeasureCursor` and `AreaMeasureCursor` — each a ~25-line registered `OBC.Component` whose only content is its `uuid` and a **descriptor** it hands to the shared `MeasureCursorEngine`. `SurfaceMeasureCursor` stays in `setup/src/` because it shares nothing with them but the click discriminator: its own coplanar-face BFS, its own measurement registry, its own CSS2D labels, no vertex snapping.

| Tool | Measurer | Descriptor carries |
|------|----------|--------------------|
| Length | `OBF.LengthMeasurement` | nothing beyond the measurer — a length is complete at two points |
| Area | `OBF.AreaMeasurement` | `color: #24a6f1`, plus Enter/NumpadEnter → `endCreation()` to close the polygon |

- **Composition, not an abstract base class — and the reason is `static uuid`.** TypeScript does not require a subclass to redeclare it, so an `AngleMeasureCursor extends MeasureCursorBase` that forgot to would inherit its parent's uuid and `components.add()` would silently overwrite a sibling in the registry. That surfaces as "turning on Angle killed Length", nowhere near the missing line. `MeasureCursorEngine` is therefore a plain class (not an `OBC.Component`), each cursor owns one, and the mistake is unreachable. This is also why the two cursor classes are near-identical boilerplate rather than deduplicated further: that duplication is the guardrail.
- **The engine owns policy; the two managers own their listeners.** `MeasureHoverManager` (raycast per `mousemove` → `CursorSurface`, one in flight at a time) and `MeasurePointerManager` (click-vs-drag, keys) each free their own listeners on `detach()`, as the `ClipperCursor` managers do.
- **Activation has nothing to wait for.** Both the cursor guide and the vertex snap are worker raycasts, so both are live the instant the listeners bind. There is no CPU geometry to extract, nothing in `world.meshes`, and no build to cancel — see § Vertex snapping below for why, and `docs/adr/0003-worker-side-snapping-over-cpu-picking-meshes.md` for what this replaced.
- **A click is a `pointerup` within 4px of its `pointerdown`** (`CLICK_SLOP`). Committing a measurement point on any pointerup would make every camera orbit drop a point.
- ⚠️ **`keydown` is on `window`, so it needs a text-input guard.** Binding to the canvas would mean measurements couldn't be deleted unless the canvas had focus; binding to `window` means Delete/Backspace typed into the models-list search or the property-table filter used to delete a measurement. `MeasurePointerManager` now bails when `e.target` is an `INPUT`/`TEXTAREA`/`contenteditable`. Note the target is *retargeted*, so an input inside a BUI shadow root reports its host element — the inputs this protects are plain React.
- ⚠️ **`delay` → `0` on activate is load-bearing, not a tuning choice.** `delay` debounces `onPointerStop`, which is what refreshes the snap preview — and `LengthMeasurement.endCreation()` commits whatever `updatePreviewLine()` (the `onPointerStop` handler) last wrote into its temp line. At the vendor default of 300 ms, clicking the second point before the debounce elapses commits the line to where the cursor was a beat ago. `AreaMeasurement` re-picks inside `create()`, so it would be safe either way. The previous value is snapshotted and restored on deactivate, not assumed. `pickerMode` is **not** touched: each `Measurement` owns its own `GraphicVertexPicker` whose mode already defaults to the one we want.
- **Length sets no `measurer.color`; Area sets `#24a6f1`.** So the two tools don't look like siblings. Preserved as-is through the refactor — making them match is a visual decision, not a structural one.

### Vertex snapping (worker-side, no CPU geometry)

Snapping is **FRAGS' job, not ours.** The measurers ask their picker for `snappings = [LINE, POINT, FACE]`; in the picker's default mode that routes `castRay({ snappingClasses })` → `FragmentsManager.raycast` → `FragmentsModel.raycastWithSnapping` per model, which snaps to real points and edges inside the worker and returns `snappingClass` / `snappedEdgeP1P2` / `facePoints` on the hit. Nothing is added to `world.meshes` — **it stays empty for the whole app's lifetime**, which is what keeps hover cheap.

- **`GraphicVertexPickerMode.SYNCHRONOUS` is the trap here.** It exists to snap against plain THREE meshes (`castRayToObjects` → `intersect(world.meshes)`), which is the *only* option in a world without fragments — and it is what this project used to do, extracting one `THREE.Mesh` per geometry instance of every model. On a real IFC that is 10k–100k meshes intersected on the main thread twice per `mousemove`, which is what made the tools unusable. Don't reintroduce it for fragment models. Full reasoning + what was rejected: `docs/adr/0003-worker-side-snapping-over-cpu-picking-meshes.md`.
- **Both measure tools run vendor-default `mode = "free"`**, so only `result.point` is ever read. `snappedEdgeP1P2` (Length's `"edge"` mode) and `facePoints` (Area's `"face"` mode) are available but unused — worth knowing before adding a mode.
- **Only two things reach the snapping path:** the measurers' picker, and `ClipAwareRaycaster`, which filters it. Selection, hover, `SpotCoordinate` and `ClipperPlacementManager` all pass no `snappingClasses` and take the plain path unchanged.
- ⚠️ **The worker does no clip culling at all** — `FragmentsModel.getClippingPlanesEvent` defaults to `() => []` and nothing in this app sets it, so the planes never reach it. An element straddling a section plane therefore offers vertices on the half the plane removed, and `ClipAwareRaycaster` filters candidates per point. Three parts of that contract are non-obvious:
  - **Within a model, keep the worker's order and take the first survivor — not the nearest.** `raycastWithSnapping` returns candidates in snap-priority order (which vertex or edge you were actually aiming at), and `FragmentsManager.raycast` takes `[0]`. Re-sorting by distance would let a far corner vertex beat the near edge under the cursor.
  - **If clipping kills every candidate, fall through to the plain `raycastAll` path — per model, never globally.** Deciding it globally starves the models that lost everything: with two coordinated models and a section active, a far surviving snap on one suppresses the near cut face on the other. Across models the survivors then merge by distance.
  - **Wiring `getClippingPlanesEvent` to `renderer.clippingPlanes` would move this filtering into the worker** and shrink the override to almost nothing — but the worker refreshes its view only on `fragments.core.update()`, so the section tool would have to pump it on every plane move, and it also drives tile-streaming culling. A real option, not taken.

### Cursor-family constructor typing

- **Three of four cursors now use the 1-arg constructor + `world` setter** (`new LengthMeasureCursor(components); cursor.world = world`), so `components.get(LengthMeasureCursor)` type-checks with **no cast** and keeps its real return type. `ClipperCursor` is the remaining holdout — its constructor also needs `viewport`, so migrating it means building its managers lazily.
- **Setting `world` on an active cursor re-binds it**, and enabling one before a world arrives is a no-op until it does. That matters because `Components.get()` **auto-constructs** a component it doesn't find: under the old 2-arg constructors that meant a cursor built with `world === undefined`, whereas now the worst case is an inert cursor.
- ⚠️ `SurfaceMeasure.tsx` needs no cast for a second reason: the whole file carries `@ts-nocheck` — the only file in `react-components/components/` that does. Its `get()` is now honest rather than merely unchecked, but dropping that suppression is a separate job (it covers far more than the cursor call).
- The three `setupLength/Area/SurfaceMeasureCursor` factories are **gone**. They returned a teardown closure that `setup/index.ts` discarded, and disposal already happens through `Components.dispose()` (called by `ViewportWrapper`), which disposes everything `isDisposeable()` in the registry.

## Drawing Editor (OBC.TechnicalDrawings — 2D annotations)

> **Not the shop-drawings "Drawing" document register.** This is a BIM-viewer capability: the ThatOpen `OBC.TechnicalDrawings` / `OBF.DrawingEditor` 2D annotation + DXF feature, ported from ThatOpen's DrawingEditor tutorial. The shop-drawings **Drawing** register (document / revision tracking) is a separate domain — see `drawing.md`. They share the word "drawing" and nothing else; don't conflate them.

The **"Drawing Editor"** workspace tab (`workspaceTabs` in `ModelsView.tsx`) lets a user annotate real building-storey floor plans projected from the loaded model(s) and export DXF. Scope is session-only: nothing persists to Supabase — the only artifact that survives is a DXF the user explicitly exports.

- **Engine component — `DrawingEditorSetup`** (`src/bim-components/DrawingEditorSetup/`): a custom `OBC.Component` registered as a singleton in `setup/index.ts`. Its constructor is cheap and creates nothing 3D — the whole engine (`OBF.DrawingEditor`, the three annotation tools, per-level `OBC.TechnicalDrawing`s, the section clip) only comes to life in `activate()`. It exposes methods (`activate`/`deactivate`, `selectLevel`, `setActiveTool`, `setLayerVisible`) and getters (`levels`, `drawing`, `viewportId`, `isProjected`, `activeToolKey`) plus an `onChanged` event; the React panes `get(DrawingEditorSetup)` and re-render on `onChanged`.
- **Lifecycle = tab lifecycle (no keep-alive).** `DrawingEditorPanel` calls `des.activate(world)` on mount and `des.deactivate()` on unmount. Switching to any other tab tears everything down — cached level drawings, the section clip, the editor — so switching away and back resets the drawing. A `_generation` counter is bumped on every activate/deactivate so stale async work (e.g. after a fast tab switch or a dev double-invoke of effects) detects it's been superseded and bails.
- **Source world.** The `OBF.DrawingEditor` binds to the **main** world via `editor.setSource(world)`; the loaded models in that world are the geometry source. There is *no* separately constructed second world — the paper-space render target is the `<bim-sheet-board>` / `<bim-paper-space>` SheetBoard in `DrawingEditorBoard.tsx`. Projection reads from **all** currently loaded models: `fragments.list` is unioned into one `OBC.ModelIdMap` (via `getItemsIdsWithGeometry`), not just the active model.
- **Real per-storey Levels.** The Levels list is built from real IFC building storeys via `components.get(OBC.Views).createFromIfcStoreys({ world })` (not a hand-rolled `getItemsOfCategories` composition). That call returns one `View` per (model, storey) with a `plane` and an `id` = storey IFC Name, and does **not** dedupe across models — so we merge the returned views ourselves by **elevation**: storeys whose `plane.constant` (world height) fall within `±0.3m` (`STOREY_MERGE_TOLERANCE`) collapse into one Levels row, first-seen name as the label, sorted descending (Roof first). The temporary `View` helpers are disposed immediately after extracting `plane`/`id` — they never linger in `views.list`.
- **Eager discovery, lazy projection.** `discoverLevels()` runs once on `activate()` (cheap metadata query) so the full Levels list appears immediately. The expensive work — creating a `TechnicalDrawing`, orienting its top-down plan viewport, and `addProjectionFromItems` — only happens the first time a level row is clicked (`selectLevel`), then is cached per session in `_levelCache`. Re-selecting a projected level just switches back; no re-projection.
- **One SheetBoard, viewport swap.** There is exactly one `<bim-paper-space label="A-01">` sheet. Switching levels removes the previously registered viewport from the sheet and adds the new level's — not one sheet per level. DXF export (per-viewport and full-sheet, via `viewportdxfexport` / `paperdxfexport` events → `downloadDxf`) is scoped to whatever is currently shown.
- **Section clip.** Selecting a level adds an `OBC.Clipper` plane on the main world just above that storey's cut plane, so the 3D viewport shows only the projected slice; the clip is swapped on each level change and removed (with `Clipper.enabled` restored) on `deactivate()`.
- **Annotation tools (MVP).** Three tools via `editor.use(...)`: Linear (`OBF.LinearAnnotationsTool`), Angle (`OBF.AngleAnnotationsTool`), Callout (`OBF.CalloutAnnotationsTool`) — fixed/default styles only (full style-customization panels are deferred). They surface as a floating toolbar in `DrawingEditorBoard` (Select / Linear / Angle / Callout + a clear-this-tool button). Each drawing gets `Visible` / `Hidden` / `Annotations` layers; layer-visibility checkboxes live in `DrawingEditorPanel`.
- **Paper-space editing.** Activating a viewport on the board (`viewportactivate`) enters paper-space edit mode: `editor.setSource(vpEl, vp)` + `enterEditMode`; board clicks call `editor.step()`. Escape cancels an in-progress placement, then exits paper mode, then clears the active tool; Delete removes the selection. Switching levels mid-annotation auto-cancels any in-progress placement and exits paper mode first (mirrors Escape) — it never blocks; committed annotations on the previous level are untouched.
- **Callout text** uses the tutorial's raw `window.prompt()` (a custom floating input is deferred). **Font** is hotlinked from ThatOpen's GitHub-hosted `.ttf` (not self-hosted), loaded fire-and-forget so a slow/blocked network can't hang activation — labels render blank until it resolves.
- **Layout.** The tab keeps the shared 3D `ViewportWrapper` visible and adds, side-by-side, the center Sheet View pane (`DrawingEditorBoard`) and a right-hand "Levels" column (`DrawingEditorPanel`: layer checkboxes, a "Show model" checkbox, and the level list). `LeftPanel`/`RightPanel` are hidden on this tab.
- **Deferred:** persisting drawings per project; a full style-editor UI; a custom floating callout input; keep-alive across tab switches; live-refreshing the Levels list when a model loads after the tab is already active; manual re-project of an already-projected level.

## Gotchas / watch-outs

- **Version lock**: ThatOpen pinned v3.4.x — verify peer deps (Three.js ^0.182, web-ifc) before any bump.
- ⚠️ **`Hoverer.enabled` / `Outliner.enabled` / `postproduction.enabled` are under a snapshot-and-restore discipline owned by the right rail** — while any viewport tool is active it holds the user's prior values in a ref and reinstates them on exit. Engine code that flips any of the three will be silently reverted the next time a tool deactivates. → the rule, and a known violation, in [`bim-viewport-toolbars.md`](bim-viewport-toolbars.md) § FX suppression.
- **Teardown / dispose ordering**: `ViewportWrapper` calls `activeComponents.dispose()` on unmount (leaving the model view). `Components.dispose()` disposes the camera/world **before** custom components that reference them, and `world.camera` is a **getter that THROWS** `"No camera initialized!"` once the camera is gone — so `if (world.camera && …)` does *not* guard it. In any custom component's `dispose()`/`_deactivate()`, wrap camera/world/renderer access in `try/catch` (pattern: `SpotCoordinate._deactivate`; `DrawingEditorSetup.deactivate` does the same around its editor/clipper/renderer cleanup). `ViewportWrapper` also wraps `dispose()` in `try/catch` as a last-resort safety net so a teardown throw can't trip React's error boundary and tear down the whole app. Regression test: `e2e/model-teardown.spec.ts`.
- ⚠️ **The near plane is `0.1`, set by us, and re-applied per camera instance.** OBC's `newCameraPerspective()` builds `PerspectiveCamera(60, aspect, 1, 1000)` — a **1 m** near plane, so anything closer is clipped and a camera parked closer than that looks *through* the surface it stopped at. `setup/src/camera-depth-range.ts` (`applyCameraDepthRange`, `CAMERA_NEAR`) lowers it, called from `create-world.ts` **and** re-called from `world.onCameraChanged`, because **every `OBC.View` constructs its own `OrthoPerspectiveCamera`** and `Views2DList.applyPerspectivePlanCamera` flips plan views straight into a fresh near=1 camera. `newCameraOrtho()` is already `0.1`. **Accepted cost:** near/far goes 1:1,000 → 1:10,000, so distant coplanar faces are likelier to z-fight and depth-based postproduction (outlines/AO) is marginally noisier. Anything that needs a closer camera must lower `CAMERA_NEAR` here rather than locally — `CursorZoom` derives its standoff from it.
- **PostproductionRenderer camera swaps need a manual resync.** The world uses `OBF.PostproductionRenderer` with postproduction **enabled** (`setup/src/highlighter.ts`, for the outliner). Its composer renders from the camera captured by the last `postproduction.updateCamera()`; swapping `world.camera` (as `OBC.Views.open()` does — it sets `world.camera = view.camera`) does **not** re-sync it, so the viewport stays on the old camera while global/material-level clip planes still apply (symptom: section cut appears but the camera never moves to the plan view). After any code that swaps `world.camera`, call `(world.renderer as any).postproduction?.updateCamera()`. Precedents: `ToolbarSettings.tsx` (projection toggle), `Views2DList.tsx` (open/close/regen). The **ViewCube** (`setup/src/view-cube.ts`) and the **toolbar projection dropdown** (`ToolbarSettings.tsx`) also don't follow camera swaps on their own — both now subscribe to `world.onCameraChanged` to rebind/refresh.
