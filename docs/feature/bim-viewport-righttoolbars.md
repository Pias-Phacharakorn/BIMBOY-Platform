# Right rail — the viewport tools (button **and** engine)

> Status: seed — expand as you work this area.
> The four tools on `ViewportRightToolbar.tsx`, each documented button-first then engine, because working on one means touching both halves. **Bottom rail, the shared dropdown idiom and cross-button hazards** → [`bim-viewport-toolbars.md`](bim-viewport-toolbars.md). **World bootstrap, camera navigation, picking, Drawing Editor** → [`bim-viewer.md`](bim-viewer.md).

## Overview

`ViewportRightToolbar.tsx` — top-right column (`absolute right-3 top-3`): Measure, Clip, Sectionbox, Coordinate. Its menus open **leftward** (`absolute right-full mr-2.5`); the bottom rail's open upward, and that direction split is load-bearing — see the toolbars guide.

**Three of the four are `activeTool`-driven, which is what makes *those three* mutually exclusive.** Sectionbox is not — see its entry below.

Neither rail owns engine state: every button reaches the engine through `components.get(...)` from `bimStore`, and holds only the UI state needed to render itself.

## Measure (`ToolbarMeasure.tsx`)

Tool list (Length, Area, Angle "Soon", Surface "Soon") plus a live measurement list per tool. Local `activeType` picks which cursor is enabled; a separate `useEffect` per cursor sets `cursor.enabled` and disables it on cleanup.

- **`ToolbarMeasure` deliberately *ignores* outside-clicks that land on the 3D canvas** while a measurement is in progress — otherwise placing the second point of a length would close the menu you are reading the result from. It is the one documented exception to the shared dropdown idiom.

### Measure tools (Length / Area / Surface)

`LengthMeasure.tsx` / `AreaMeasure.tsx` / `SurfaceMeasure.tsx` supply each tool's button + result list. Angle is a "Soon" placeholder. Nothing persists — measurements die with the viewport.

**Length and Area are one component family; Surface is a different animal.** `src/bim-components/MeasureCursor/` holds `LengthMeasureCursor` and `AreaMeasureCursor` — each a ~25-line registered `OBC.Component` whose only content is its `uuid` and a **descriptor** it hands to the shared `MeasureCursorEngine`. `SurfaceMeasureCursor` lives in its own directory and shares *conventions* with them, not code: `MeasureCursorDescriptor` is built entirely around `MeasurerLike` (an `OBF.Measurement` with `create()`/`endCreation()`), and Surface has no vendor measurer at all. It owns its own coplanar-face BFS, measurement registry and CSS2D labels, and does no vertex snapping.

| Tool | Measurer | Descriptor carries |
|------|----------|--------------------|
| Length | `OBF.LengthMeasurement` | nothing beyond the measurer — a length is complete at two points |
| Area | `OBF.AreaMeasurement` | `color: #24a6f1`, plus Enter/NumpadEnter → `endCreation()` to close the polygon |

- **Composition, not an abstract base class — and the reason is `static uuid`.** TypeScript does not require a subclass to redeclare it, so an `AngleMeasureCursor extends MeasureCursorBase` that forgot to would inherit its parent's uuid and `components.add()` would silently overwrite a sibling in the registry. That surfaces as "turning on Angle killed Length", nowhere near the missing line. `MeasureCursorEngine` is therefore a plain class (not an `OBC.Component`), each cursor owns one, and the mistake is unreachable. This is also why the two cursor classes are near-identical boilerplate rather than deduplicated further: that duplication is the guardrail.
- **The engine owns policy; the two managers own their listeners.** `MeasureHoverManager` (raycast per `mousemove` → `CursorSurface`, one in flight at a time) and `MeasurePointerManager` (click-vs-drag, keys) each free their own listeners on `detach()`, as the `ClipperCursor` managers do.
- **Activation has nothing to wait for.** Both the cursor guide and the vertex snap are worker raycasts, so both are live the instant the listeners bind. There is no CPU geometry to extract, nothing in `world.meshes`, and no build to cancel — see § Vertex snapping below for why, and [ADR-0003](../adr/0003-worker-side-snapping-over-cpu-picking-meshes.md) for what this replaced.
- **A click is a `pointerup` within 4px of its `pointerdown`** (`CLICK_SLOP`). Committing a measurement point on any pointerup would make every camera orbit drop a point.
- ⚠️ **`keydown` is on `window`, so it needs a text-input guard.** Binding to the canvas would mean measurements couldn't be deleted unless the canvas had focus; binding to `window` means Delete/Backspace typed into the models-list search or the property-table filter used to delete a measurement. `MeasurePointerManager` now bails when `e.target` is an `INPUT`/`TEXTAREA`/`contenteditable`. Note the target is *retargeted*, so an input inside a BUI shadow root reports its host element — the inputs this protects are plain React.
- ⚠️ **`delay` → `0` on activate is load-bearing, not a tuning choice.** `delay` debounces `onPointerStop`, which is what refreshes the snap preview — and `LengthMeasurement.endCreation()` commits whatever `updatePreviewLine()` (the `onPointerStop` handler) last wrote into its temp line. At the vendor default of 300 ms, clicking the second point before the debounce elapses commits the line to where the cursor was a beat ago. `AreaMeasurement` re-picks inside `create()`, so it would be safe either way. The previous value is snapshotted and restored on deactivate, not assumed. `pickerMode` is **not** touched: each `Measurement` owns its own `GraphicVertexPicker` whose mode already defaults to the one we want.
- **Length sets no `measurer.color`; Area sets `#24a6f1`.** So the two tools don't look like siblings. Preserved as-is through the refactor — making them match is a visual decision, not a structural one.

### Surface: coplanar faces from worker geometry

- **Geometry is fetched per element, not held resident.** `world.meshes` is empty for the app's lifetime ([ADR-0003](../adr/0003-worker-side-snapping-over-cpu-picking-meshes.md) deleted the picking meshes that used to fill it), so fragment models expose no CPU triangles on the main thread. The hovered element's geometry comes from `model.getItemsGeometry([localId])` → `MeshData[]`, welded into world space via `part.transform` then `model.object.matrixWorld`. **Never reintroduce per-instance picking meshes to make this synchronous** — that is exactly what ADR-0003 removed for costing framerate on hover alone.
- **Two caches, both in `SurfaceMeasureEngine`.** An item cache keyed `modelId:localId` (insertion-ordered LRU, cap 32) holds the welded soup; a face cache keyed `modelId:localId:seedTriangle` holds the extracted rings. The worker fetch is **gated on the pointer settling** (120 ms) so sweeping the cursor across a model costs nothing, while a cache hit resolves synchronously and feels instant. Both caches are dropped wholesale on `fragments.list.onItemSet`/`onItemDeleted` — deliberately coarse, since matching the event payload to a model is more fragile than rebuilding ≤32 entries.
- ⚠️ **"One surface" means connected ∧ same plane ∧ same side.** A neighbouring triangle joins the face only if it shares a *welded* vertex (quantised at `1e-4`, because IFC duplicates vertices at identical coordinates for per-face normals — index-keyed adjacency halts the walk at the seed triangle), **and** `normal.dot(seed) >= 0.9998` **signed**, **and** the plane offsets match within `1e-4`. The signed test is load-bearing: `Math.abs()` there accepts the anti-parallel far side of a wall, which roughly doubles the reported area. The plane-offset test is what keeps two parallel-but-offset faces apart.
- **The seed triangle is found geometrically**, from the hit point plus the hit normal — not from `RaycastResult.faceIndices`. The previous implementation read `result.faceIndex`, which is not a property of the FRAGS result at all, so it silently seeded from triangle 0 of a batched instanced geometry and never worked after the worker migration.
- **Openings are subtracted.** `extractCoplanarFace` returns `{ outer, holes }` — the longest-perimeter boundary ring plus every interior ring — so a wall face containing a window reports the wall's net area, and the hover preview renders the opening as an actual hole via `THREE.Shape` + `holes`.

### Vertex snapping (worker-side, no CPU geometry)

Snapping is **FRAGS' job, not ours.** The measurers ask their picker for `snappings = [LINE, POINT, FACE]`; in the picker's default mode that routes `castRay({ snappingClasses })` → `FragmentsManager.raycast` → `FragmentsModel.raycastWithSnapping` per model, which snaps to real points and edges inside the worker and returns `snappingClass` / `snappedEdgeP1P2` / `facePoints` on the hit. Nothing is added to `world.meshes` — **it stays empty for the whole app's lifetime**, which is what keeps hover cheap.

- **`GraphicVertexPickerMode.SYNCHRONOUS` is the trap here.** It exists to snap against plain THREE meshes (`castRayToObjects` → `intersect(world.meshes)`), which is the *only* option in a world without fragments — and it is what this project used to do, extracting one `THREE.Mesh` per geometry instance of every model. On a real IFC that is 10k–100k meshes intersected on the main thread twice per `mousemove`, which is what made the tools unusable. Don't reintroduce it for fragment models. Full reasoning + what was rejected: [ADR-0003](../adr/0003-worker-side-snapping-over-cpu-picking-meshes.md).
- **Both measure tools run vendor-default `mode = "free"`**, so only `result.point` is ever read. `snappedEdgeP1P2` (Length's `"edge"` mode) and `facePoints` (Area's `"face"` mode) are available but unused — worth knowing before adding a mode.
- **Only two things reach the snapping path:** the measurers' picker, and `ClipAwareRaycaster`, which filters it. Selection, hover, `SpotCoordinate` and `ClipperPlacementManager` all pass no `snappingClasses` and take the plain path unchanged.

- ⚠️ **The measure tools cannot be regression-tested by browser automation.** `@thatopen/components@3.4.8` gates `Hoverer` and `Measurement` picks on user-input events, so synthetic hover/click from a driven browser commits a `0.00 m` line — a false failure that looks exactly like a broken snap. Verify measure with a human at the mouse; automate the rest of the viewport freely. → [ADR-0018](../adr/0018-thatopen-3-4-8-patch-bump.md).

- **`SnapResolver` is now the vendor's own main-thread snap**, added in 3.4.8 — snapping from *cached shell* geometry, not the per-instance extraction [ADR-0003](../adr/0003-worker-side-snapping-over-cpu-picking-meshes.md) deleted. It is present in the installed typings and unused here; the worker path still works and stays. Read ADR-0003's premise with this in mind before treating "snapping is FRAGS' job" as the only option.
- ⚠️ **The worker does no clip culling at all** — `FragmentsModel.getClippingPlanesEvent` defaults to `() => []` and nothing in this app sets it, so the planes never reach it. An element straddling a section plane therefore offers vertices on the half the plane removed, and `ClipAwareRaycaster` filters candidates per point. Three parts of that contract are non-obvious:
  - **Within a model, keep the worker's order and take the first survivor — not the nearest.** `raycastWithSnapping` returns candidates in snap-priority order (which vertex or edge you were actually aiming at), and `FragmentsManager.raycast` takes `[0]`. Re-sorting by distance would let a far corner vertex beat the near edge under the cursor.
  - **If clipping kills every candidate, fall through to the plain `raycastAll` path — per model, never globally.** Deciding it globally starves the models that lost everything: with two coordinated models and a section active, a far surviving snap on one suppresses the near cut face on the other. Across models the survivors then merge by distance.
  - **Wiring `getClippingPlanesEvent` to `renderer.clippingPlanes` would move this filtering into the worker** and shrink the override to almost nothing — but the worker refreshes its view only on `fragments.core.update()`, so the section tool would have to pump it on every plane move, and it also drives tile-streaming culling. A real option, not taken.

### Cursor-family constructor typing

- **Three of four cursors now use the 1-arg constructor + `world` setter** (`new LengthMeasureCursor(components); cursor.world = world`), so `components.get(LengthMeasureCursor)` type-checks with **no cast** and keeps its real return type. `ClipperCursor` is the remaining holdout — its constructor also needs `viewport`, so migrating it means building its managers lazily.
- **Setting `world` on an active cursor re-binds it**, and enabling one before a world arrives is a no-op until it does. That matters because `Components.get()` **auto-constructs** a component it doesn't find: under the old 2-arg constructors that meant a cursor built with `world === undefined`, whereas now the worst case is an inert cursor.
- **All four measure/surface UI files are now typed.** `SurfaceMeasure.tsx` used to carry `@ts-nocheck` — the only file in `react-components/components/` that did — which is precisely why the `faceIndex`/`faceIndices` bug above survived a release unnoticed. The suppression is gone and its `components.get()` is checked rather than merely unchecked.
- The three `setupLength/Area/SurfaceMeasureCursor` factories are **gone**. They returned a teardown closure that `setup/index.ts` discarded, and disposal already happens through `Components.dispose()` (called by `ViewportWrapper`), which disposes everything `isDisposeable()` in the registry.

## Clip (`ToolbarClip.tsx`)

Add plane · Clear all, plus a plane checklist (select, show/hide, delete per row).

- **Placement is one-shot.** `handleEnterPlacement` sets `activeTool = "clip"` and enters placement; when `ClipperCursor` reports it has stopped placing (plane placed, or Escape), the sync effect resets `activeTool` to `"select"`. The button label switches to "Placing (ESC to cancel)" meanwhile.
- **`activeTool` is also the interlock:** if any other tool becomes active while placement is armed, an effect calls `clipper.exitPlacementMode()`.
- ⚠️ **`components.get(ClipperCursor as any)` is deliberate** — `ClipperCursor`'s 3-arg constructor doesn't match what `Components.get()` expects. It is the last component in the repo still needing this cast; see § Section tool below.

### Section tool (OBC.Clipper — interactive cut planes)

`ClipperCursor` (`src/bim-components/ClipperCursor/`) wraps `OBC.Clipper` and is the engine behind this menu. Max 6 planes. Nothing persists — planes die with the viewport.

**A cut plane has four visual parts, and none of them is `SimplePlane`'s own quad.** OBC ships plane, helper and drag arrow welded together; we use the plane's maths, ignore its geometry, and build the rest:

| Part | What it is | Where it lives |
|------|-----------|----------------|
| **band** | A closed rectangular ring — outer edge 3× the fitted footprint, inner edge inset 4% of the shorter side (`planeBand.ts`). Interior empty. **This is the click target on an unselected plane** | `GizmoAxis` overlay — `depthTest: false`, clipping suspended |
| **outline** | `LineLoop` on the band's outer edge, the crisp boundary | the overlay, beside the band |
| **fill** | Solid grey at the cut cross-section, from `OBF.ClipStyler` (→ § Fills) | `world.scene` — depth-tested and clipped, unlike the band |
| **axis gizmo** | A `GizmoAxis` `"plane"` handle. The only **drag** handle, and only on the selected plane | the overlay |
| ~~carrier quad~~ | `SimplePlane._planeMesh` — nothing is parented to it any more, so `plane.size`, `autoScale` and the hidden-material trick are all gone | — |
| ~~drag arrow~~ | `SimplePlane`'s own `TransformControls` — permanently suppressed | — |

- **A plane draws a border band, not a fill, and that band is what you click to switch to it.** Those two facts are one decision: [ADR-0002](../adr/0002-section-plane-outline-only.md) refused a pickable plane because *"a plane grabbable **anywhere it is visible** is grabbable across most of the screen"* — a band is visible only around the footprint perimeter, so the middle of the plane, where the geometry you want to click lives, is never pickable. → [ADR-0011](../adr/0011-clickable-border-band-cut-planes.md), which supersedes ADR-0002.

  ⚠️ **Making the *full quad* pickable was attempted on 2026-08-05 and caught in review.** `_downListener` is a capture-phase listener on `window` that consumes pointerdown for any hovered target, so a footprint-sized target killed **camera orbit and element selection** across most of the viewport. `Raycaster.intersectObjects` also ignores material depth state, so a plane behind a wall still won the click. **The invariant that replaced it lives at `AxisDragManager._pickHandle`: every pick target must be a thin, deliberate handle — never a surface spanning the model.** A band qualifies; a quad, a fill, or anything covering the footprint does not.

- **Exactly one thing per plane is pickable, and selection decides which** — that split is forced by `canDrag(id)` being keyed on plane id, which could not otherwise tell an arrow grab from a band click on the same plane:

  | Plane state | Drawn | Pickable | `canDrag` | Result |
  |---|---|---|---|---|
  | enabled, **unselected** | band + outline | the **band** | `false` | click → selects it, nothing moves |
  | enabled, **selected** | band + outline | the **arrow**, and the **diamond** | `true` | arrow drag moves the cut; diamond drag moves the gizmo within it |

  ⚠️ **A band click is consumed** (`preventDefault` + `stopPropagation`), like an arrow grab — so switching plane changes the selection and nothing else, and your element selection survives. The cost is that camera orbit cannot start *on* a band.

- **Band and outline live in the overlay pass, not `world.scene`** — the same place `SectionBox` puts its twelve edges. Not cosmetic: the band is the click target, and since `Raycaster` ignores material depth, a depth-tested band could be invisible yet clickable. Drawing without depth makes what you see and what you can hit the same object, so that mismatch cannot exist — and it keeps the pick synchronous, where consulting `ClipAwareRaycaster` would have forced an `await` that `stopPropagation()` cannot survive. ⚠️ **Two accepted consequences:** bands draw through geometry in front of them, and they are no longer clipped by other enabled planes.

- ⚠️ **Overlay objects are not followed automatically.** `GizmoAxis.overlay` deliberately skips its per-frame follow-and-rescale loop so world-scale objects keep their size, so `ClipperOutlineManager.syncTransform` must be called whenever a plane moves — from `onDrag`, and after a refit. Skip it and the plane cuts somewhere its own border is no longer drawn.

- ⚠️ **`plane.visible` is pinned `false`, permanently.** With nothing parented to the carrier quad, all that setter still reaches is the vendor's own quad, helper and `TransformControls` arrow — none of which should ever render. It survives enable/disable too: `SimplePlane.enabled = true` restores `_visibilityBeforeDisabled`, which was captured as `false`. `suppressDefaultArrow` is kept as belt-and-braces.
- **Outline colour states the world axis the plane's normal runs along, or grey when it runs along none** (`colorOf()` in `GizmoAxis`, which the gizmo's arrow reads too — one rule, one direction, so the two cannot disagree). Interaction state therefore rides on **opacity** (idle 0.45 → selected 0.85 → hovered/dragging 1.0), not hue. ⚠️ Not on line weight: `LineBasicMaterial.linewidth` is ignored by `WebGLRenderer` (lines are always 1px) — carrying state there needs `Line2` fat-line geometry.

  | normal | colour | what it cuts |
  |--------|--------|--------------|
  | ±Y | blue | a plan / level cut (horizontal) |
  | ±X | green | an elevation cut facing X |
  | ±Z | red | an elevation cut facing Z |
  | none of them | **light grey** | a cut skewed to the grid — a raking wall, a non-orthogonal bay |

  ⚠️ **Vertical is world Y here, not Z.** IFC authors Z-up; FRAGS presents the model Y-up. So a plan/level cut wears a **blue** outline rather than a red one — a reader assuming Z-up reads that row as red and concludes the mapping is broken. The "what it cuts" column exists so the table is readable without that assumption.

  ⚠️ **"Runs along" means within `AXIS_ALIGNMENT_DOT` (0.9998, ≈1.15°), and that tolerance is deliberately loose.** Too tight and an orthogonal wall whose triangle normals carry float noise greys out, so the common case looks broken; too loose and a wall raked by a degree wears an axis colour, which is a lie nobody can see. `axisOf()` used to **snap** to the nearest axis with no tolerance at all, which is why a 44° cut was painted as though square — and why the same snap put the grabbable arrow up to 54.74° off the cut. → [ADR-0009](../adr/0009-section-plane-gizmo-local-frame.md).
- **Each outline is the model's own footprint on that plane, not a square** — the models' bounding box has its 8 corners projected into the plane's frame, and the resulting min/max rectangle becomes the outline (`planeFit.ts` → `fitBoxToFrame`). `plane.autoScale = false` (OBC's default is camera-relative, which reads as a badge near the gizmo rather than a plane slicing the model).

  **For a cut square to the grid this is the matching `SectionBox` face, enlarged threefold**, which is the point: the two sectioning tools draw the same *boundary*, at different sizes. It replaced a square of edge = bbox diagonal, which was oversized on purpose so it would clear the footprint from *any* angle.

  - **The drawn rectangle is `PLANE_FIT_SCALE = 3` × the fit** (`ClipperOutlineManager`). Only width and height are scaled — `centerX`/`centerY` are not — so the rectangle grows concentrically around the footprint and the model stays in the middle of its own cut plane whichever corner was clicked. At 1× the band ring landed *on* the geometry it cuts and the plane read as part of the model; at 3× it sits clear of the model entirely, tints nothing, and is easier to hit for switching plane. The cost is real and was accepted: you must pull the camera well back to see a whole plane, and with several planes enabled their rings overlap far more.
    - ⚠️ **The scale is applied in `_applyFit`, never inside `fitBoxToFrame`.** `scripts/check-gizmo-frames.mjs` Group D2 imports that function directly to assert its slide-invariance — the one assertion that lands on production code rather than a re-implementation beside it. Padding the fit itself would leave the check passing while testing a value it does not name.
    - **`BAND_RATIO` is deliberately outside the scale**, so the ring keeps its 4%-of-the-shorter-side proportion and the plane looks identical, only bigger.
    - **`extent()` reports the scaled rectangle**, not the fit, so the gizmo's refit clamp (below) is bounded by what the user can actually see. A gizmo parked near a corner is never yanked to a boundary that was never drawn.
    - ⚠️ **This changes only what is drawn.** `OBC.Clipper`'s plane is mathematically infinite, so a bigger rectangle does not cut more of the model, and the `ClipStyler` fills stay bounded by real geometry.
  - **`plane.size` is out of the picture entirely.** It was briefly pinned to 1 while the outline was a child of `_planeMesh` (a single uniform scalar cannot express a rectangle). Now nothing is parented to that mesh, so `Clipper`'s list-wide `size` setter — which walks every entry with no notion of who created it (ADR-0005 fact 3) — can no longer reach a cut plane's visuals at all.
  - **Projecting the corners, not the box.** `Box3.applyMatrix4` re-axis-aligns and so grows the result; the corner shadow is exact for the AABB given. It also means **no `axisOf()` branch** — a skewed cut gets a tight rectangle instead of a fallback square, and the code works on a model rotated for site north, where `AXIS_ALIGNMENT_DOT` (≈1.15°) would have called nothing axis-aligned.
  - **Shape and colour now answer different questions.** `colorOf` still greys a skewed normal, so a skewed cut draws a **grey** rectangle fitted to its own footprint. Do not read the colour as a statement about the shape.
  - **A drag never needs a refit.** Dragging slides the helper along its own local +Z, which changes every projected corner's local *z* and leaves local x/y alone — so the rectangle is invariant under exactly the motion the tool allows. That property comes from projecting into the *plane's* frame; the same code against world axes would not have it.

  ⚠️ **Measured when a plane is created, not at load time.** `BoundingBoxer.addFromModels()` unions each `model.box`, and a model is in `fragments.list` while still loading (FRAGS reports `isBusy` as `!_isLoaded || _isProcessing || pendingRequests`), so an `onItemSet`-triggered read can legitimately find an empty box. A plane is only ever created by a click, so that read is always post-processing. The `onItemSet` hook stays to resize *existing* outlines and **bails on an empty box** rather than falling back — falling back is what used to leave a 10-unit outline inside a 40 m building. `ClipperOutlineManager` is the only boxer consumer in the repo that reads at load time; `view-cube.ts` and `ToolbarSettings.tsx` both read on user action.

  ⚠️ **`addFromModels()` unions *every* loaded model, so with several structures in the scene a plane placed on one building gets a rectangle spanning all of them.** Known and unresolved — the open question (fit to the clicked model, the union, or the selection?) is recorded in [ADR-0010](../adr/0010-sectioning-arbiter-and-fitted-plane-outlines.md) § Consequences. Invisible in a single-model scene, which is why it went unnoticed.
- **The gizmo spawns where you clicked, and you can slide it anywhere inside the cut.** → [ADR-0013](../adr/0013-movable-cut-plane-gizmo.md). A detached `Object3D` anchor per plane carries it, the same pattern `SectionBox` uses for its face arrows, but the offset from helper to anchor is now **owned state** (`_gizmoOffsets`, a `THREE.Vector2`) rather than the fitted centre. Spawning at the click point is the offset `(0, 0)` — `_createPlane` already passes the clicked point as `createFromNormalAndCoplanarPoint`'s coplanar point, so `plane.helper.position` *is* the click point and the feature was the **removal** of a `centerOffset` term, not the addition of a spawn rule.
  - **The offset lives in the helper's local X/Y**, not world space — invariant under sliding the cut along its own normal, which is the only thing the arrow drag does. All three conversions are in `src/gizmoOffset.ts` (`localOffsetToWorld`, `worldPointToLocalOffset`, `clampOffsetToExtent`) so `_syncAnchor` and `onDrag` cannot hold one exact and one approximate copy of the same arithmetic — and so `scripts/check-gizmo-frames.mjs` Group D can drive the real code headlessly, which nothing inside `ClipperCursor` allows.
  - **Free while dragging, clamped only on refit.** `outlines.onFitChanged` clamps the offset back into the new rectangle via `extent(planeId)`, closing the case of an offset outliving a footprint that just shrank — without a clamp fighting the pointer mid-gesture.
  - **`ClipperPlaneState.gizmoMoved` is the one place drag state reaches React**, committed once on drag end from a dirty bit set inside `onInPlaneDrag` (not from the `draggingId → null` transition, which would light up on a press-and-release that moved nothing). It only exists so `ToolbarClip`'s per-plane **reset** button can disable itself; `clipper.resetGizmo(id)` zeroes the offset and re-syncs.
  - ⚠️ **The anchor carries the helper's rotation as well as its offset position**: the `"plane"` gizmo form grabs its target's local +Z, so an unrotated anchor would aim the arrow down world Z instead of along the cut. (`SectionBox`'s anchors are the opposite case — they must *never* be rotated. See § Section box.)
- **Dragging is our own pointer handling, and lives in the shared `AxisDragManager`** (see § GizmoAxis) — `ClipperCursor` supplies `getAxis` (the plane's normal), `getOrigin` (the **anchor**, since that is where the arrow is) and `onDrag` as callbacks, so the manager never learns what clipping is. ⚠️ **`onDrag` subtracts the in-plane offset before writing `plane.helper.position`, and re-syncs the anchor after.** The manager returns `startOrigin + axis × offset`, i.e. the anchor displaced purely along the normal; the offset from anchor to helper is perpendicular to that, so subtracting it recovers the helper's position **exactly**, not approximately. Skip the re-sync and the arrow stays put while the plane moves. **`pointerdown` is captured on `window`, not the canvas.** camera-controls and the highlighter listen on the canvas itself, and a capture listener on the same element still runs *after* them (target-phase listeners fire in registration order), so the event has to be stopped one level up. Only thin handles are pickable — a gizmo picker or a plane's border band — so that stop only ever fires over one of those. The drag builds a camera-facing plane containing the normal, intersects the pointer ray with it, and projects the offset onto the normal — so a tilted plane still moves exactly perpendicular to itself. Camera is disabled for the duration, the same way `SimplePlane.changeDrag` does it.
- **Component layout follows MiniMap/PropertyTable**: `index.ts` holds the class, `src/` holds managers, and **each manager owns and frees its own objects** (`ClipperOutlineManager`, `ClipperFillManager`, `ClipperPlacementManager`). Disposal is therefore local, not one central routine. The drag manager is the exception — it moved out to `GizmoAxis/src/AxisDragManager.ts` when `SectionBox` needed the same pointer handling, since it is owned by neither component. It still takes a `pickTargets: () => { mesh, id }[]` callback rather than a reference to the gizmo layer.
- ⚠️ **`components.get(ClipperCursor as any)` in `ToolbarClip` is deliberate, not sloppiness.** Its 3-arg constructor doesn't match what `OBC.Components.get()` expects. It is now the **last** cursor still doing this: all three measure cursors have moved to the 1-arg constructor + `world` setter (see § Cursor-family constructor typing). `ClipperCursor` needs `viewport` as well as `world`, and its constructor builds all three managers immediately, so migrating it means making that construction lazy — a separate job, not a one-line change.
- **Planes created by other features are left alone.** `ClipperCursor` styles only planes it creates (no `Clipper.onAfterCreate` hook), so the Drawing Editor's own section clip — which sets `plane.visible = false` itself — is untouched.

### Fills at the cut (`ClipperFillManager` → `OBF.ClipStyler`)

A cut discards geometry, so a sliced wall renders as an open shell. `ClipperFillManager` fills that cross-section so it reads as solid material. → [ADR-0012](../adr/0012-section-fills-via-clipstyler.md).

- **One fill-only style, shared by every plane.** `fillsMaterial` set and `linesMaterial` **omitted**, which the vendor documents as generating no lines at all. That omission is why nothing here imports `LineMaterial` from `three/examples` or drags fat-line machinery into the bundle.
- **`items: { All: { style } }` — no `Classifier`, no `ItemsFinder`.** `ClipEdgesItemStyle.data` is documented as *"If not set, all items cut will be styled"*, so the tutorial's whole grouping section is unnecessary for a uniform fill. Per-category styles (walls one colour, doors another) can be added later without rework.
- ⚠️ **`ClipStyler`'s auto-update cannot fire in this app, and we supply the refresh.** `createFromClipping` links two things to the plane: `onDisposed → edges.dispose()`, which works and is why `link` stays on, and `onDraggingEnded → edges.update()`, which **never fires** — it is triggered only by `SimplePlane`'s own `TransformControls`, permanently disabled here. Without our own trigger a fill would render once at the plane's birth position and stay there while the cut moved away.
- **The refresh is derived, once per drag gesture.** `ClipperFillManager.noteDragState` takes the drag manager's `draggingId` on every state change; a transition from an id to `null` means that drag ended. No new option on `AxisDragManager` — the same reasoning as § Sectioning interlock. `update()` is async and rebuilds cut geometry against every loaded model, which is why it is not per-frame. ⚠️ **Deliberate consequence: the fill is stale mid-drag and snaps on release** — acceptable because the band and outline follow live, so the cut's position is never in doubt.
- **A model load refreshes every fill** (`outlines.onFitChanged`): no plane moved, but there is new geometry for the existing cuts to pass through.
- ⚠️ **Style registration must precede plane creation.** `ClipEdges.items` carries a guard that silently rejects a style name the styler does not already know — creating first leaves every plane with an empty item map, **no fill and no error**. The order is enforced in the manager's constructor.
- **Setting the item is what generates the first fill.** `items.onItemSet` calls the vendor's own `create(style, data)`, so no initial `update()` is needed.
- **The fill is `0xb8b8b8`, not the tutorial's black.** Poché reads as solid *against the void*, and the convention is dark-on-light. This viewer is the reverse — `--color-bg` is `oklch(10.5% 0.012 255)` and `scene.background` is `null`, so a black fill would sit at the void's own lightness and read as a **hole**. Neutral, too: the bands and arrows already carry the axis palette.
- ⚠️ **Fills live in `world.scene`, so they *are* depth-tested and *are* clipped by other planes** — unlike the band and outline. Correct per part (a fill is cut material inside the model; a band is an annotation that must not be hidden by it), but it means one plane's appearance spans two render passes.
- **Suspension is free.** `_syncVisibility` drives fill visibility from `planeState.enabled`, and `SectioningArbiter` suspends by calling `togglePlane`, so a suspended cut loses its fill along with its band.
- ⚠️ **`SectionBox` gets no fills.** The two sectioning tools therefore render cuts differently, which is visible the moment you switch between them. `ClipStyler.create()` accepts a bare `THREE.Plane`, so the box's six faces are eligible and the cost is small (one `update()` per face drag, six on *Reset*/*Fit*) — held back for scope, not blocked.

**Vendor traps in `ClipEdges`**, all read off the pinned v3.4.x bundle while chasing a displaced-fill bug ([ADR-0014](../adr/0014-frags-worker-from-node-modules.md)). None is reachable through the public API, so none can be configured away:

- ⚠️ **A fill cannot be bounded.** `ClipEdgesCreationConfig` exposes only `id`, `items`, `link` and `world` — no extent, rectangle or bounds — and `ClipEdges.plane` is a `THREE.Plane`, infinite by definition. So a fill covers wherever that infinite plane meets **any** geometry, and can legitimately extend past the band that visually frames the cut. Bounding it would mean four side clipping planes on the fill material plus `localClippingEnabled` on the renderer — a decision, not a config change.
- ⚠️ **`ClipEdges.create()` sections every model in `fragments.list`, unconditionally** — no visibility test. `ClipEdges.three` is added straight to `world.scene`, never parented to a `model.object` (one group spans all models, so there is nothing to parent it to), which means a fill neither inherits a model's transform nor disappears when the model is hidden. Nothing in the viewer toggles `model.object.visible` today, so this is latent — but any future per-model hide feature must hide fills itself.
- ⚠️ **The fills mesh is never `frustumCulled = false` and its bounding volume is never recomputed.** `getStyleMeshes` sets that flag on the **lines** mesh only, and `updateMeshes` then assigns `geometry.attributes.position` directly and calls `setIndex`, leaving `boundingSphere` stale. Symptom would be a fill *vanishing* at certain camera angles — not yet observed, but it is the first thing to check if one does.
- ⚠️ **`getStyleMeshes` awaits between its cache check and its cache write.** Two concurrent `updateMeshes` calls for the same model+style can both miss the cache, both build a mesh and both `three.add(...)`; the loser of the race is never updated again but stays in the scene. Not confirmed to have fired here — it was the prime suspect for the displaced fill and the worker turned out to be the cause — but the window is real in the vendor code.

## Sectionbox (`ToolbarSectionBox.tsx`)

`Section box` on/off · `Fit to selection` · `Reset to model`, plus a live extents pane reading X/Y/Z min→max and size to 2 decimals.

- ⚠️ **The one right-rail button that does *not* use `activeTool`.** It sits on this rail because it is a sectioning tool, but a crop is view state, not a pointer mode — so it is exempt from the FX suppression below and is **not** mutually exclusive with Measure/Clip/Coordinate. A cut plane and a box can both be live, and you can measure inside a box. Wiring it to `activeTool` would have cost the selection outliner and the whole postproduction pass for as long as the box cropped.
- **Holds no authoritative state**: mirrors `SectionBox.state` through `onStateChanged`, as `ToolbarClip` mirrors `ClipperCursor`.
- **The store gates, the engine serves** — the same split as `ToolbarVisibility`: `bimStore.selectedElementIds` drives whether `Fit to selection` is enabled, but the handler acts on the live `highlighter.selection.select`, because `selectionMap` is a clone one event behind.
- **`Fit to selection` and `Reset to model` both switch the box on** if it was off. Clicking either means you want to see the result.
- Sits between Clip and Coordinate on the rail.

### Section box (a crop volume, outside OBC.Clipper)

`SectionBox` (`src/bim-components/SectionBox/`) crops the model to a resizable box and is the engine behind this menu. Nothing persists — the box dies with the viewport. → why it does not use `OBC.Clipper`, and every rejected alternative: [ADR-0005](../adr/0005-section-box-outside-clipper.md).

- **Six bare `THREE.Plane`s, registered with `world.renderer.setPlane(true, plane)`** — no `OBC.Clipper`, no `SimplePlane`, nothing in `Clipper.list`. `OBC.Views` clips the same way, so this is a vendor path, not a workaround. Consequences: `ClipperCursor`'s `MAX_PLANES = 6` budget is untouched, and `Clipper`'s list-wide `size`/`material`/`visible` setters cannot reach the box.
- ⚠️ **Each plane's normal points *inward*.** three.js keeps the half-space where the signed distance is positive, and the box interior is what must survive. `BoxFacesManager.apply()` builds each one from `setFromNormalAndCoplanarPoint(-outward, faceBound)`, so the sign is only decided in one place.
- ⚠️ **`Clipper.enabled` clips nothing** — its setter stores a flag and fires an event; `SimplePlane.enabled` is the real switch. So the two `_clipper.enabled` writes in `ClipperCursor` (in `_syncVisibility` and `dispose`) are inert bookkeeping, and the Clip menu cannot silently un-crop a box. Left as-is deliberately; fixing it means deciding what `Clipper.enabled` is *for*.
- **It never touches `bimStore.activeTool`, and that is load-bearing.** A crop is view state you keep on while selecting, measuring and reading properties. Since the right rail suppresses `Hoverer`, `Outliner` *and* `postproduction` whenever `activeTool !== "select"`, wiring the box to it would cost selection outlines and the whole post pass for as long as the box cropped. So the box is **not** mutually exclusive with Measure or Coordinate. The reserved `BimTool` member `'section'` stays unused. ⚠️ **It *is* mutually exclusive with Clip — but through `SectioningArbiter`, not `activeTool`.** See § Sectioning interlock. The `activeTool` mechanism is still rejected for the reason above.
- **`ClipAwareRaycaster` needed no changes.** It filters against `renderer.three.clippingPlanes`, which is the array `setPlane` maintains — so selecting, hovering and measuring inside the box were correct for free.
- **Extents come from `BoundingBoxer` on user action only, never at load time**, for the reason § Section tool documents: `addFromModels()` unions each `model.box` and a still-loading model can legitimately yield an empty one. ⚠️ **Deliberate consequence: a model loaded while the box is on does not grow the box.** A crop the user set must not jump; `Reset to model` is how a re-measure is requested. `Fit to selection` pads by one min gap so the selected elements aren't sliced by their own box.
- **Inward face drags clamp to a min gap; outward drags are unbounded.** `max(camera.three.near × 2.5, diagonal × 0.001, 0.05)` — derived from the live near plane exactly as `CursorZoom` derives its standoff, so the two cannot drift. Dragging a face out past the model is how you effectively uncrop that side. Without the clamp, a face crossing its opposite leaves two non-overlapping half-spaces and the whole model vanishes.
- **One arrow per face, in `GizmoAxis`'s `"arrow"` form** — one of two (`"plane"`, `"arrow"`); the box omits `canDrag`, since every face is always draggable. Each follows a detached `THREE.Object3D` anchor at its face centre. Anchors are in no scene on purpose — `GizmoAxis` only reads `follow.matrixWorld` after `updateWorldMatrix`, which resolves with no parent. Gizmos are built once and toggled by `visible`, not created and destroyed per activation.
- **Faces take `AXIS_COLORS` directly** — the same green/blue/red table as § Section tool, and the box passes **no palette** to `GizmoAxis.create()` because a face's axis genuinely *is* a world axis, so the default is already right. `OFF_AXIS_COLOR` can never apply here: the box is axis-aligned by construction.
- ⚠️ **The box relies on its anchors never being rotated.** `GizmoAxis` follows its target's full transform, rotation included, so an anchor is kept as a bare `Object3D` that only ever receives `position.copy()`. That identity quaternion is what makes rotation-following a no-op here and is why no `orientation` option exists — rotate an anchor and its arrow rotates with it.
- **The 12-edge outline is one `LineSegments` with `depthTest: false`, in the overlay pass** (`gizmoAxis.overlay.add`), sized by scaling a unit `EdgesGeometry` cube — two writes per box change instead of a geometry upload. ⚠️ **Clipping was not the reason for `depthTest: false`:** coplanar geometry survives three.js clipping (fragments are discarded at signed distance `< 0`), which is why the cut planes' own outlines render. *Depth* was — every box edge borders the cross-sections its planes cut, so a depth-tested wire z-fights there. **Accepted:** all twelve edges show through the model.
- **Component layout follows `ClipperCursor`**: `index.ts` holds the class and the box arithmetic, `src/` holds managers it owns and frees (`BoxFacesManager`, `BoxOutlineManager`). `BOX_FACES` in `src/types.ts` is the single enumeration of the six faces — planes, gizmos and the menu's extent rows all walk it, so none can disagree about what exists.
- **1-arg constructor plus `world`/`viewport` setters**, with the faces manager, gizmos and drag manager built lazily once both have arrived — so `components.get(SectionBox)` needs **no cast**, and `ClipperCursor` remains the only component that does.
- ⚠️ **`OBC.Views` writes to the same `renderer.setPlane` array**, so opening a 2D view while a box is live crops by both. Left alone — `SectioningArbiter` mediates the box and the cut planes only, and pulling `Views` in means giving it a notion of being suspended that it does not have.

### Sectioning interlock (`SectioningArbiter`)

`SectioningArbiter` (`src/bim-components/SectioningArbiter/`) keeps the box and the cut planes from cropping at once: start one and the other switches off; switch the winner off and the loser comes back as it was. → why, and every rejected alternative: [ADR-0010](../adr/0010-sectioning-arbiter-and-fitted-plane-outlines.md).

- **Neither tool knows about the other.** No mutual import (which between two classes carrying static `uuid` fields is fragile under bundling), no new events, and **no new methods** — `SectionBox` needed no code change at all. The arbiter composes `onStateChanged`, `togglePlane`, `enable`/`disable` and `active`, all of which already existed. This is what [ADR-0005](../adr/0005-section-box-outside-clipper.md)'s "forcing an interlock means teaching each feature about the other" was worried about, and it is avoided rather than accepted.
- ⚠️ **It derives who is cutting; it is not told — and that is the load-bearing part.** It reads `sectionBox.active` and `planes.some(p => p.enabled)`, diffing against its own previous view to spot a transition. A bespoke `onActivated` pair looks cleaner and **cannot work**: it signals activation only, so nothing ever fires when the winning tool is switched *off*, and the loser stays suspended with no way back. If you find yourself "simplifying" this into an event, that is the bug you are reintroducing.
- ⚠️ **A `_reconciling` flag guards re-entrancy.** Suspending and restoring drive `togglePlane`/`enable`/`disable`, each of which fires the `onStateChanged` the arbiter listens to. Without the flag, a restore re-enters, suspends the tool it is restoring *from*, and clobbers its own snapshot.
- **Suspension is reversible and snapshotted.** There is no undo in this app, so nothing is destroyed. The arbiter records which planes were enabled before the box took over, so a restore cannot switch on a plane the user had deliberately switched off — the `fxBaselineRef` pattern from `ViewportRightToolbar`. A plane deleted meanwhile is skipped; a plane the user toggles on by hand while the box crops overrides the interlock and **discards the stale snapshot**.
- **Cut planes are suspended through the same `togglePlane` a user clicks**, which is what makes it safe: that path ends in `_syncVisibility()` and so re-applies `suppressDefaultArrow`. ⚠️ Necessary, because `SimplePlane.enabled = true` restores the plane's remembered visibility and with it the vendor's `TransformControls` arrow — the triple-duty setter § Section tool documents.
- ⚠️ **It bails when there is no live renderer.** `SimplePlane.enabled` *throws* without one, and `SectionBox._teardownWorldParts` drops `_active` silently, so during world teardown there is nothing safe to do and nothing worth doing.
- **`planeState.enabled` stays the *actual* cutting state**, so the Clip menu never claims a plane is cutting when it is not. That makes `ToolbarClip`'s "Suspended — the section box is cropping" hint **required, not decoration**: without it a user who placed three planes opens the menu, finds three rows switched off, and reasonably concludes they were lost. The arbiter's `suspendedTool` getter is what the toolbar reads.

## Coordinate (`ToolbarCoordinate.tsx`)

Add coordinate · Clear all, plus a list of placed points showing X/Y/Z to 3 decimals with per-row delete. Subscribes `SpotCoordinate.onLabelsChanged` to stay in sync. Placement is **double-click** on the model, which the button label states.

- **Ownership swap, for the whole tool session:** `activeTool === "coordinate"` disables `OBF.Highlighter` and enables `SpotCoordinate`; anything else does the reverse. A second effect repeats the restore on unmount, so navigating away mid-tool can't leave selection dead.

## GizmoAxis (shared overlay axis gizmos)

`src/bim-components/GizmoAxis/` is a general engine service, not a clipping concept: "give me a handle at this transform, in that transform's own frame, always drawn on top" — plus, since the section box landed, "and draw this object in that same pass." It lives in this guide because both its consumers — § Section tool and § Section box — are right-rail tools.

- **Two gizmo forms, chosen by `AxisGizmoOptions.form`.** `"plane"` (the default, what cut planes use) is a long double-headed arrow along the followed transform's **local +Z**, two short inert arms on local X and Y at `IN_PLANE_LENGTH_RATIO` (0.45, so the normal reads ~3× longer), a centre diamond, and a picker cylinder centred on the origin. `"arrow"` (what box faces use) is a single arrow along `grabAxis` towards `direction`, no diamond, with the picker **offset fully onto its own side** — on a thin box a centred picker would make the near face's handle grab the far one. The `"arrow"` form also allocates materials for one axis instead of three.
- ⚠️ **`"plane"` was called `"axes"`**, and `grabAxis` is now **optional** — required only by `"arrow"`. The `"plane"` form always grabs local +Z, because `OBC.SimplePlane` builds its helper with `helper.lookAt(this.normal)` and `Object3D.lookAt` aims local +Z at its target. That vendor coupling lives in **one** constant, `PLANE_NORMAL_AXIS` in `axis-gizmo-mesh.ts` — if OBC changes the convention, that is the only line to move.
- **One colour table, four values.** `AXIS_COLORS` (world axis → hue) plus `OFF_AXIS_COLOR` for a direction that names no axis. `axisOf()` returns the axis a direction runs along within `AXIS_ALIGNMENT_DOT`, or **`null`** — that `null` is the whole point, and the difference from the snapping version it replaces. `colorOf()` wraps it with the grey fallback. → [ADR-0009](../adr/0009-section-plane-gizmo-local-frame.md).
- ⚠️ **`OFF_AXIS_COLOR` is light grey, not black.** Achromatic is the intent — no hue, no axis — but the viewport background is a dark gradient (`oklch(21%…)` → `oklch(9%…)` in `style.css`) and gizmos render `depthTest: false` over open sky as often as over geometry, so black would be invisible exactly where these gizmos float. White fails the mirror-image way against the pale model, since an achromatic colour can only differ in lightness.
- **`framePalette(quaternion)` builds a `"plane"` gizmo's colours, and the *caller* calls it.** A gizmo is drawn in local space and cannot know where its rotation aims each arm, so `ClipperCursor` derives the palette from `plane.helper`'s world quaternion and passes it in. Consequence worth knowing: **each arm is coloured by its own world axis**, so a square cut shows green/blue/red exactly as it did pre-ADR-0009, and a wall raked *in plan* keeps its **blue** vertical arm while the other two grey out. Only a cut skewed in every direction greys wholly.
- ⚠️ **`buildAxisGizmo` returns `grabColor`, and the hover highlight restores *that*.** A `"plane"` gizmo's colours come from the caller's frame, not from an axis letter, so there is nothing to look the colour up *in* afterwards — re-deriving from `AXIS_COLORS[grabAxis]` would repaint a skewed plane's grey arrow **red** on un-hover. This is also why `AxisGizmoHandle` no longer carries `grabAxis`: the restore was its last reader.
- **`overlay.add(obj)` / `overlay.remove(obj)` host raw `Object3D`s in the shared scene**, skipped by the per-frame follow-and-rescale loop that `create()`'s handles go through. That skip is the point: the section box's outline is **world**-scale, so passing it through `create()` would shrink and grow it with zoom. ⚠️ **`remove()` detaches, it does not dispose** — the caller keeps ownership, and `GizmoAxis.dispose()` likewise only detaches, because disposing there would double-free whichever component tore down second.
- ⚠️ **Naming debt, recorded not paid:** a component called `GizmoAxis` now also serves non-gizmo overlays. Renaming it to something like `SceneOverlay` reaches `ClipperCursor`, this guide, ADR-0002 and ADR-0005 for no behaviour change.
- **`AxisDragManager` (`src/AxisDragManager.ts`) is the shared pointer handling**, used by both `ClipperCursor` and `SectionBox`. It knows nothing about clipping: `pickTargets`, `getAxis`, `getOrigin`, `onDrag` and `onSelect` are the whole contract, and the consumer applies (and clamps) the dragged position itself. It was `ClipperCursor/src/ClipperDragManager.ts` until the box needed it — the pre-box behaviour is `git show fc285d2:src/bim-components/ClipperCursor/src/ClipperDragManager.ts` if plane dragging ever looks wrong.
- **Two drag modes, one manager** (→ [ADR-0013](../adr/0013-movable-cut-plane-gizmo.md)). A `pickTargets` entry carries `mode?: "axis" | "inPlane"`, defaulting to `"axis"`, and an optional `onInPlaneDrag(id, position)` receives the 2-DOF result. **`SectionBox` needed zero changes** — it omits `mode` and never passes `onInPlaneDrag`, so `"inPlane"` is inert for anything that does not opt in. ⚠️ **The *contract* is reused verbatim; the internals genuinely branch.** `"axis"` builds a camera-facing plane containing the axis (to dodge degenerate ray angles) and projects onto the axis; `"inPlane"` builds the **literal cut plane** and hands over the raw intersection unprojected. `getAxis` serves both — the in-plane drag needs the same normal to build its plane from.
- ⚠️ **`_pickHandle`'s priority pass is scoped *per id*, and that is the whole safety of it.** An id's `"inPlane"` hit preempts **that same id's** `"axis"` hit — necessary because the diamond sits entirely inside the arrow's grab cylinder (corners reach `0.424`, pick radius is `0.525`), so a nearest-hit sort could never let it win. Results then merge back into one nearest-hit ordering across ids. A **global** override (all `"inPlane"` beats all `"axis"`) is correct today only by accident: `_syncVisibility` makes exactly one gizmo pickable, so there is no second diamond to out-rank a nearer plane's arrow. Land multi-select and a farther plane's diamond would silently steal a click, with no compile error and nothing in `check:gizmo` to catch it.
- **One overlay scene and one render pass for every gizmo**, registered on `world.renderer.onAfterUpdate`: it suspends `clippingPlanes`, sets `autoClear = false`, renders, then restores. One shared scene means the second and third consumers cost no extra pass. All materials are `depthTest: false`, which is what makes a handle grabbable wherever it is visible — including when the model stands in front of it.
- **1-arg constructor plus a `world` setter** (`new GizmoAxis(components); gizmoAxis.world = world`), as `SpotCoordinate`/`ArSession`/`Hoverer` do. Consequence worth knowing: `components.get(GizmoAxis)` needs **no cast**. This is the pattern the cursor family is migrating *to* — the three measure cursors now follow it too, leaving `ClipperCursor` as the only component still needing one. Setting `world` re-registers the pass.
- **`create({ follow, grabAxis })` returns an opaque `AxisGizmoHandle`** carrying `picker`, `visible`, `highlighted` and `dispose()`. Consumers keep handles however they like, so there is no shared key namespace to collide in and a disposed handle can't be reused. `ClipperCursor` keeps `Map<planeId, handle>` and builds its own pick list from `handle.picker`/`handle.visible`.
- **It follows its target's position *and* rotation** — via `applyFollowTransform` (`src/follow-transform.ts`), so a gizmo sits in its target's own frame. For a cut plane that is what makes the grabbable arrow run along the real cut normal however the plane is skewed. **Scale is the one component ignored**: screen-constant sizing comes from `GIZMO_VIEW_FRACTION` (a fraction of the viewport's world-space height, handling perspective *and* orthographic cameras) — **the one knob for gizmo size**. Rotation is read with `getWorldQuaternion`, which is scale-safe: `plane.size` does scale a `SimplePlane`, on `_planeMesh` rather than the helper.
- **Rotation-following is unconditional, not an `orientation: "world" | "follow"` option** — which the code used to predict in a comment. Nothing wants `"world"`: the box's anchors are never rotated, so `"follow"` is right for both callers. ⚠️ Consequence: a future consumer that follows a *rotating* object gets a rotating gizmo. The rejected option is the answer if one appears.
- ⚠️ **`applyFollowTransform` is a separate function so it can be tested.** The per-frame loop is a closure on `renderer.onAfterUpdate` and needs a `World` plus a WebGL context, so `scripts/check-gizmo-frames.mjs` cannot drive it; it calls this function instead. Keep the loop calling it rather than inlining the arithmetic, or the check silently stops covering production.
- **Arrow/outline agreement is structural, not computed.** A cut plane's outline is a child of `_planeMesh` under the same `plane.helper` the gizmo follows, so both inherit one transform. This is why the gizmo takes the helper's quaternion rather than being handed the exact normal: ⚠️ a plan cut's helper frame is legitimately **0.00573°** off its own normal (three.js nudges `_z.z += 0.0001` when the normal is parallel to `up` — the degenerate `lookAt` case), so an independently-exact arrow would *disagree* with the outline. It is also why `check-gizmo-frames.mjs` uses a 0.01° tolerance and not 0.
- **Only the arrow matching the plane's colour is grabbable**, wrapped in an invisible cylinder, and it is drawn at `GRAB_AXIS_EMPHASIS` (×1.5) — length, cone *and* picker, so what you can grab stays identical to what you can see. The `"plane"` form additionally shortens its two inert arms to `IN_PLANE_LENGTH_RATIO` (0.45), putting the grab arrow at roughly 3× them. It turns `HIGHLIGHT_COLOR` (yellow) while hovered or dragged — yellow collides with nothing in the table, `OFF_AXIS_COLOR` included. The other two arrows are inert: pulling them would move the outline without changing where the model is cut.
- ⚠️ **Cones are aimed with `quaternion.setFromUnitVectors(CONE_APEX, direction)`, never by composing Euler angles.** A previous `rotZ`/`rotX` scheme sent the −Z cone's apex to **+Z** — its fallback flip about Z fired on top of the flip about X and undid it, so one red arrowhead pointed inward. With a target direction there is no order, sign or per-axis constant left to get wrong. The antiparallel −Y case is safe: `setFromUnitVectors` detects `dot + 1 < EPSILON` and falls back to a half-turn about Z.
- ⚠️ **Cross-component imports inside `bim-components/` must be relative** (`"../GizmoAxis"`), *not* the `@/*` alias that `CLAUDE.md` mandates elsewhere. `tsconfig.json` excludes `src/bim-components/**`, so `vite-tsconfig-paths` never rewrites aliases in that folder: an aliased import **type-checks and then fails the Rollup build**. Every pre-existing file there already imports relatively for this reason.

**Accepted consequence:** the outline lives in `world.scene`, so another enabled plane can clip part of it away. Immunity would mean moving it to the overlay scene, which would also make it immune to *depth* — drawing over the model instead of behind it. `WebGLRenderer.clippingPlanes` is global with no per-material opt-out, so those two properties can't be separated.

## FX suppression (the rail itself)

**The right rail suppresses viewport FX while any tool is active.** On the first transition of `activeTool` to anything other than `select`, `ViewportRightToolbar` snapshots `OBF.Hoverer.enabled`, `OBF.Outliner.enabled` and `postproduction.enabled` into a ref, disables all three, and **restores that snapshot** — not defaults — on return to idle, and again on unmount if a tool is still active.

Rationale: `CursorSurface` is the on-model guide while a tool runs, so the element hover-highlight and the outliner pass are redundant, and they cost a raycast plus a fullscreen post pass every frame.

⚠️ **Anything that toggles those three must respect the snapshot or it will be silently reverted.** This rule binds engine code too, not just toolbars — [`bim-viewer.md`](bim-viewer.md) § Gotchas carries a pointer back here for that reason.
