📌 Goal

Kill the ~10 s freeze (and ongoing hover lag) when activating the Length/Area measurement tools on a big model. The cursor guide should appear instantly; vertex-snapping should stay available without brute-forcing thousands of un-accelerated meshes on every mouse move.

⚖️ Pros & Cons

ProsCons
Cursor guide appears instantly — the 10 s wait is gone because the hover no longer waits on the mesh extraction.For a brief moment after activating on a huge model, click-to-snap may not snap until the background build finishes (cursor + free placement still work).
BVH (computeBoundsTree) makes the per-move CPU intersect fast, so hovering stays smooth even with picking meshes present. Uses ThatOpen's already-installed accelerated raycast — no new dependency.Building BVH adds work to the (now background) extraction and some memory per unique geometry.
Per-model cache means re-activating a tool / switching Length↔Area doesn't re-extract.Cache needs invalidation when models load/unload mid-session — added logic + a correctness surface to get right.
Disabling OBF.Hoverer while a tool is active removes a redundant per-move raycast/highlight (your idea); CursorSurface is the guide.Background build + enabled-guard adds a little async complexity vs. the current straight-line await.

📁 Files Changed

[MOD] src/bim-components/setup/src/length-measure-cursor.ts    - attach cursor/hover synchronously first (instant guide); call shared helper in background (not awaited) with an enabled-guard; drop duplicated setup + console.log
[MOD] src/bim-components/setup/src/area-measure-cursor.ts      - same treatment as length cursor

❓ Open Questions

One design alternative, not blocking: instead of extracting + BVH-ing picking meshes at all, we could rely on the fragments' native snapping (raycastWithSnapping / snappingClasses, which castRay already supports) and drop the whole world.meshes extraction. That would be the leanest fix (no extraction, no memory, no cache) but is a larger behavioral change to vertex-snapping that I can't validate without on-device testing — so this plan keeps the safer "extract-in-background + BVH" path and leaves native snapping as a future simplification. Say approve to implement as planned, or tell me to pursue the native-snapping route instead.
