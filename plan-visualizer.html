⚖️ Pros & Cons

ProsCons
Matches the actual "AR example" reference the user pointed at (spin-the-model demos) without requiring any coordinate/georeferencing work this project doesn't have yet. Model still floats at a fixed 2m offset with no real-world anchoring — it will visibly drift/clip through walls as the user walks around, since there's still no hit-test/floor lock. Not solved by this change, and looks odd if not expected.
Smallest possible diff: one file (ArModelViewer.tsx), no touch to the dormant ArSession hit-test path, no schema/route changes. Y-axis-only turntable means the user can't tilt the model to inspect its underside/roofline from above/below — a deliberate simplification, not a limitation of the gesture code itself.
Turntable constraint (Y-axis only) keeps the building always upright — can't end up sideways or upside-down from an accidental gesture. No pinch-to-scale in this round, so a model that's still awkwardly sized (too big/small relative to real surroundings) can't be manually corrected — only recenterAndScale's fixed 1.5m target applies.
Reuses the existing pointer-based interaction pattern already common in this codebase (no new dependency — plain pointerdown/pointermove/pointerup on the renderer's DOM element). Drag-to-rotate and the picker overlay panel both live in the same full-screen area; if the picker panel is open during a drag near the bottom of the screen, the two capture zones must be kept from fighting over touch events (picker keeps pointer-events: auto, rest of screen stays the drag surface).
